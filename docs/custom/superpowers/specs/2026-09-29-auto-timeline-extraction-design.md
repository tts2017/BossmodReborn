# リプレイからのタイムライン自動抽出 設計

日付: 2026-09-29
関連: `docs/superpowers/specs/2026-09-26-unified-timeline-design.md`(統合タイムライン)、`docs/superpowers/plans/2026-09-26-unified-timeline-results.md`、memory `external-timeline-audit-2026-09-24`

## 1. 目的と成功条件

遊ぶだけで、そのコンテンツのタイムラインがリプレイから自動で作られ、更新されるようにする。今の抽出は CLI(`tools/replay_timeline_extract`)だけで、手で実行してユーザーフォルダに置く必要がある。

成功条件:

- デューティを出て録画が止まると、数分以内にそのコンテンツの自動タイムラインが更新され、次から予告に使われる。
- 精度の悪いもの(死者の宮殿のように周回をまたいで再現しない窓)は自動で除外される。
- プレイ中のゲームを止めない(裏スレッド、メモリは要約の分だけ)。
- 手で置いたタイムラインは触らず、そちらを優先する。

ユーザーの決定(2026-09-29): 起動は「録画終了時の自動 + 設定画面の手動ボタン」、品質ゲートは「窓単位の holdout」、順位は「手動が優先、自動は FFLogs・埋め込みより優先」、方式は「リプレイごとの要約キャッシュ」。

## 2. 構成と流れ

### 2.1 起動

- 録画完了: `ReplayManagementWindow.StopRecording` で、閉じたファイルのパスを通知するイベントを新設する(今は完了の通知が無い)。自動抽出はこれを購読し、そのファイルを要約キューに入れる。
- 手動: `BossModuleConfig.DrawCustom` に「全リプレイから自動タイムラインを作り直す」ボタンを置く。リプレイフォルダの全 `*.log` のうち要約が無い・古いものを要約し、全 zone を再構築する。既存リプレイの取り込みもこのボタンで行う。
- 設定 `BossModuleConfig.AutoExtractTimelines`(既定 true、`UseExternalTimelineHints` に依存)。false なら録画完了では何もしない(ボタンは使える)。
- 起動時の一括取り込みはしない(374 本で数時間の CPU を使うため)。

### 2.2 作業キュー

裏スレッド 1 本(優先度 BelowNormal)。仕事は 2 種類。

- **要約**(リプレイ 1 本): `ReplayParserLog.Parse` で解析し、`FindPulls` の各 pull を要約(2.3)に落として、`<timelines>\auto\cache\<リプレイのファイル名>.json` に保存する。解析したリプレイはすぐ手放す。終わったら、その要約に含まれる zone の再構築を積む。
- **再構築**(zone 1 つ): `auto\cache\` の全要約からその zone の pull を集め、抽出(2.3 の要約から)→ 品質ゲート(3 章)→ `<timelines>\auto\<zone>-auto.json` を書く(または書かない/消す)→ `TimelineStore.ReloadInBackground()`。

キューは重複をまとめる(同じリプレイ・同じ zone は 1 回)。進捗(残りの仕事の数、処理中の内容)と最終実行の要約 1 行を設定画面に出す。

キャッシュの有効性: 要約は元リプレイのサイズ・更新時刻と要約形式の版を持ち、すべて一致すれば再解析しない。元リプレイが `MaxReplays` で消えても要約は残し、再構築に使い続ける。

### 2.3 要約(pull ごと)

抽出器が pull から読むものだけを持つ。これで今の抽出結果とバイト単位で同じものが作れることを検証の条件にする(5.1)。

- zone、開始時刻(実時刻。ボスの組の並び順に使う)、長さ、ボス OID の並び
- ボスの技: (pull 開始からの秒、アクション ID、詠唱開始/効果)。`BossEvents` と同じ抽出(汎用オートアタック除外)
- NoTarget 窓と、ボス対象不可の窓: (開始秒、終了秒)。`NoTargetWindows` / `BossUntargetableWindows` の結果
- 名前付きボスごとに: OID、MaxHP、存在期間、HP の変化点(秒、現在 HP)。`PrimaryBossHPPercent` の置き換えに使う

抽出器の入力をこの要約に変える。`FindPulls(Replay)` は残し、要約を作る関数を足す。`Build` / `BuildBossSet` / `Extract` は要約を受け取る版に置き換え、`Extract(IEnumerable<Replay>)` は「要約してから抽出」の薄い包みにする。CLI(`tools/replay_timeline_extract`)とハーネス(`tools/timeline_hint_harness` の holdout)も要約経由になる。

### 2.4 解析中の副作用

裏で解析するとき、`ReplayBuilder` はモジュール管理を動かして `Encounters` を記録する。pull の区切りが変わらないよう、モジュールは今までどおり動かす。ただし `ExternalPlannerTimeline.Apply`(`UseExternalPlannerTimelines` が有効なとき、モジュールの状態機械をタイムラインで置き換える)は、自動抽出の解析中は無効にする(スレッドに閉じた抑止フラグ)。解析中に自動タイムラインがモジュールへ反映されて抽出結果が循環するのを断つため。

既知の残りリスク: モジュール管理が共有設定の `Modified` イベントへ登録する処理は主スレッドと競合し得る。リプレイ閲覧機能の裏解析と同じ性質のもので、今回は変えない。

### 2.5 読み込みと順位

- `TimelineStore` はユーザーフォルダ直下に加えて `auto\` 直下の `*.json` も読む(`auto\cache\` は読まない)。
- `TimelineSource` に `AutoReplay` を足す(既存の値の後ろ、= 5)。自動抽出の出力はこの Source で書く。
- 順位: 手動 Replay > User > **AutoReplay** > FFLogs > Cactbot > EventTrigger。
- 手で置いたファイルは読み書きしない。

## 3. 品質ゲート(窓単位の holdout)

再構築のたびに、ボスの組(同じボス OID の pull の集まり)ごとに検査する。

1. pull が 3 本未満の組は、同期点(states)だけ残して窓を出さない。
2. 組の pull を 1 本ずつ外し、残りから `BuildBossSet` と同じ方法で作った sequence の公開対象の窓(NoTarget、8.5 s 以上、確信度 0.5 以上)を、外した pull の実際の NoTarget 窓と照合する。時刻 0 は pull 開始。
   - 的中: 予測した開始が、実際の窓の [開始 −5 s, 終了] に入る。
   - 外れ: 予測した開始の −5〜+30 s に、実際の NoTarget 窓(長さ不問)が 1 つも始まらない。
   - 外した pull がその時刻まで続いていなければ(ワイプ)、照合しない。
   - HP 分岐の組は、外した pull の分岐点での主ボス HP としきい値から兄弟を選び、その兄弟と照合する。しきい値が無い場合、分岐点以降の窓は照合しない。
3. 全 pull から作った sequence の公開対象の各窓について、holdout で「その窓に対応する予測」が照合できた pull が 2 本以上あり、そのうち 3 分の 2 以上で的中していれば残す。満たさない窓は sequence から除く(同期点は残す)。対応付けは、holdout の予測窓のうち開始が全体版の窓の開始に最も近いもの(±10 s 以内)とする。
4. 書くかどうか:
   - 残った公開対象の窓が zone 全体で 0 本なら書かない。
   - その zone に AutoReplay より下位のタイムライン(FFLogs・Cactbot・EventTrigger)があり、その最上位の公開対象の窓の数が、自動の残存窓の数より多ければ書かない(zone 単位でしか選べないので、一部のボスしか覆わない自動版で他のボスの窓を失わないため)。
   - 書かないと決めたときは、その zone の以前の自動ファイルがあれば消す。
5. 検査の結果(zone、組ごとの pull 数、残した窓と捨てた窓、書いたかどうかと理由)を `auto\report.txt` に上書き保存する。

## 4. 失敗時の扱い

- 解析の失敗(空の結果、例外)は「失敗」として要約に記録する。同じサイズ・更新時刻のファイルは再試行しない。例外は `Service.Log` に記録して次の仕事へ進む。
- プラグイン終了時は作業をキャンセルして終了を待つ。ファイルは一時名に書いてから置き換える(書きかけを残さない)。
- 要約形式の版が合わない要約は読まず、作り直しの対象にする。
- 出力フォルダ(`auto\`、`auto\cache\`)が無ければ作る。書き込みに失敗したらその仕事を失敗として記録して続ける。

## 5. 検証

1. 同等性: 要約経由の CLI 出力が、変更前の CLI 出力と一致すること(`tl_alliance` の 1304/1368/1248、Clyteum、`tl_branch4` の 1304)。ハーネスの holdout を要約経由にして、統合タイムラインの計測 7 条件(アライアンス holdout・自データ内、旧 47 本 3 条件、FFLogs、自リプレイ)で CSV が変更前と一致すること。
2. 品質ゲート: 死者の宮殿 14 セットで、自動ファイルを書かないか、書いてもハーネスで誤予告が出ないこと。アライアンスと Clyteum で窓が残り、自動ファイルでのハーネスの的中と誤予告が手動ファイルと同等以上であること。
3. 単体チェック(`tools/external_timeline_regression`): 要約の往復、キャッシュの無効化(サイズ・時刻・版)、ゲートの判定(再現する窓は残り、しない窓は落ちる合成データ)、順位(AutoReplay は手動 Replay/User より下、FFLogs より上)、上書きしない条件、キューの重複まとめ。
4. 負荷: 要約 1 本の作成時間とメモリの最大値、Clyteum 94 本の再構築時間を測って記録する。
5. 配置: テスト環境に入れ、手動ボタンで既存リプレイを取り込み、`auto\report.txt` を確認する。

## 6. 対象外

起動時の自動取り込み、FFLogs からの自動取得、要約の他人との共有、ゲーム内でのタイムライン編集、フォロワーを動かす holdout(ハーネスで行う)。

## 改訂(2026-09-29)

実装と最終レビューの修正で、次のとおり確定した。上の本文は当初の設計として残す。3 章の 2・3、2.4 の「既知の残りリスク」は、この節が優先する。

- **品質ゲートの判定**(3 章の 2・3 を置き換える)。1 本抜きで作り直した予測を、抜いた pull の実際の NoTarget 窓と比べる。
  - 的中(hit): 予測の開始が、長さ 8.5 秒以上の実際の窓の [開始 −5 秒, 終了] に入る。
  - 確認(confirmed): 的中であるか、長さ **3 秒以上**の実際の窓が [予測の開始 −5 秒, 予測の開始 +30 秒] に始まる。3 秒はフォロワーの `ContradictionGrace` と同じ値(`AutoTimelineGate.MinConfirmSeconds`)。それより短い途切れは確認にならない。
  - 窓を残す条件: 評価できた pull が 2 本以上、そのうち 3 分の 2 以上が確認、かつ**的中が 1 本以上**。
  - HP 分岐の組では、分岐点より前の窓は両方の兄弟が持つ。数えるのは早い側の兄弟の窓と、遅い側の兄弟の窓のうち判定時刻以降に始まるものだけ(下位ソースとの比較でも同じ数え方)。
- **pull の上限**: ボスの組ごとに開始時刻の新しい K 本だけを使う指定を足した(`AutoTimelineGate.Evaluate` の `maxPullsPerSet`、CLI の `--max-pulls`)。プラグインの既定は上限なし。Clyteum 97 本で K = 20・30・50 を試すと、ハーネスの誤予告は 59 → 65 に増え、アライアンスは 3 通りとも変わらなかったため。
- **戦闘中は止める**: 裏スレッドは、プレイヤーが戦闘中のあいだ次の仕事を始めない。1 秒ごとに確かめ、プラグイン終了時はすぐに抜ける。設定画面の状態は `paused (in combat)`。手動ボタンには「数分かかることがあり、デューティの外での実行を勧める」と出す。
- **要約キャッシュの読み込み**(4 章に追加): 開けないキャッシュ(ほかのプロセスが掴んでいる等)は書き込みと同じく再試行し、それでも読めなければその再構築を失敗にする。一部の pull だけで自動ファイルを書いたり、正しい自動ファイルを消したりはしない。壊れた・不完全・版違いのキャッシュは除外し、パスごとに 1 回だけログに出す。
- **失敗した要約の数**: 設定画面の状態の行の末尾に `failed summaries: N` を出す(最後の一括取り込み、またはプラグイン起動からの数)。
- **2.4 の残りリスクは解消**: リプレイを解析するときのモジュール管理(`ReplayBuilder`)は、共有設定の `Modified` に登録しない。デモモジュールも読み込まない。
- プラグイン終了で止まった録画は `RecordingFinished` を出さないので、自動では取り込まれない。手動ボタンで取り込む。
